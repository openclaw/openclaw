## Shared preparation policy remains a proposal

The exact name `dictationPreparation` is absent from the current `UiSettings` declaration, its `UiPreferences = Omit<UiSettings, "token">` alias, explicit settings load/save implementation, `SYNCED_PREFS` descriptor map, and strict server `ui.prefs` schema. There is no current shipped support for the proposed policy group in these owners.

The existing browser preference owner uses Gateway-origin scoping via `settingsKeyForGateway`. `loadUiPreferences` and `saveSettings` enumerate normalized fields explicitly; `patchSettings` delegates to the existing save/change-notification path. Adding a type property alone would not establish persistence, defaults or validation. Some existing profile metadata has its own identity-scoped handling, so the general browser settings record must not be described as owning every preference.

`configSync: false` does **not** mean browser-only. The current descriptor map gives that setting to `fontUi`, `fontChat`, `tabIcon`, `background` and `sidebarEntries`; these also have profile preference mappings. The current push logic allows applicable profile-backed writes when the authenticated profile/permission conditions hold. `changedServerUiPrefs` iterates the explicit `SYNCED_PREF_KEYS` list, not every local setting. Therefore an accepted browser-only preparation policy must stay outside the synchronization descriptor map as well as the strict server `ui.prefs` schema; setting `configSync: false` is insufficient.

The attachment's proposed 1-KiB `dictationPreparation` group remains separate from snippet bodies and from the unchanged 4,096-byte profile-value ceiling. It is not a new platform limit, accepted content store or runtime proof of sync exclusion. A future accepted change must use the existing owner, implement explicit local load/save/default/validation, preserve unrelated synchronized preferences and verify that no preparation policy is transmitted through the server preference path.
