# Channel-turn benchmark

Measure an inbound text message through a bundled channel plugin, a real Gateway agent turn, and outbound reply delivery. By default the fixture uses `qa-channel`, the local `qa-lab` HTTP bus, and the mock OpenAI provider. It needs no live channel account or model credential.

From an installed checkout, build the private QA runtime, then run the benchmark:

```sh
OPENCLAW_BUILD_PRIVATE_QA=1 OUTPUT_SOURCE_MAPS=1 \
  node --import ./scripts/tsx.mjs scripts/build-all.mts qaRuntime
node --import ./scripts/tsx.mjs scripts/bench-channel-turn.mts
```

Use `--resources` for per-turn process, main-thread and native worker CPU counters and warm-window memory snapshots. `evidence.json` also records inbound-to-final-outbound time, settled dispatch time, and outbound message count. Worker snapshots use `Worker.cpuUsage()` once at each turn boundary, without an inspector or heap walk. Raw thread IDs and counters, sampling wall time and main-thread sampling CPU remain in the evidence, so analysis can report worker churn and measurement overhead. Process CPU includes worker and native background threads; process minus main-thread CPU is not a worker-only measurement.

Use a separate `--cpu-profile` run for attribution. It captures native `--cpu-prof` profiles through shutdown and a bounded `warm.cpuprofile` with worker profiles, CPU counters, worker-message counts and diagnostics using the existing private benchmark IPC. The bounded capture starts after the cold turn and ends after the tenth warm dispatch settles; inter-turn settling remains inside that window. Profiling is instrumented evidence, not an unprofiled latency result.

For warm-turn changes, publish the acceptance rule before running: one cold turn excluded, ten warm turns per sample, at least five samples per arm interleaved baseline/candidate, identical synthetic conversation and mock provider. Report median, p95 and range for first/final outbound latency, dispatch settlement, main CPU and total process CPU; report matched worker CPU separately from the boundary counters, plus outbound counts and warm memory. A win requires a measured reduction in the targeted operation and CPU or latency, no increase in outbound work, and no user-facing metric regression. A 20% regression in any cell stops the change. Keep cold and warm results separate and record host load and runtime.

Use `--entry /path/to/entry.js` to select an already-built runtime. The benchmark prints its artifact directory as `OUTPUT <path>` and sets a nonzero exit code on failure. `TMPDIR` controls the parent directory. Apply the host's build/benchmark capacity limit when running alongside other jobs.

The workload contains one cold and ten warmed turns in one direct conversation. Sender, conversation, message IDs, prompts and mock replies are fixed. With `qa-channel`, inbound timestamps are synthetic too, and each turn waits for the matching full reply and the channel's acknowledged inbound cursor, which follows dispatch, preview cleanup and receipt settlement. The existing one-second settling window separates turns. The fixture uses isolated HOME, state, configuration, workspace and loopback ports; it stops its Gateway, mock provider and bus before returning.

`evidence.json` contains turn identities, child PIDs, readiness, graceful shutdown, the final bus snapshot (with `qa-channel`), and inbound-to-first-outbound latency for each turn. The first outbound may be a streaming preview. SIGINT and SIGTERM stop the child process groups and bus before exiting. Read the child logs when readiness, delivery or shutdown fails. Artifacts are intentionally retained for inspection; remove the printed directory after collecting results.

`--channel telegram` or `--channel slack` replaces `qa-channel` with the bundled Telegram or Slack plugin and a local Crabline provider server (`@openclaw/crabline`): Telegram long-polls the Crabline Bot API, and the benchmark signs Crabline's Slack event and posts it to the Gateway's `/slack/events`. Every Slack Web API call passes through a front in the benchmark, which records it and answers `users.info` (a fixed user) and reactions itself, since Crabline's Slack server does not implement them. Inbound messages carry provider IDs, which `channel-turns.json` maps to turns: Slack's `ts` from Crabline, and Telegram `message_id`s that the benchmark assigns (1000, 2000, ...) so the map is published before Crabline can hand the update to the waiting poll. The first turn starts after Telegram's first completed poll or Slack's first accepted `auth.test`, followed by the one-second wait. A turn ends when the message carrying the reply's last line was accepted and no provider call other than Telegram's `getUpdates` followed for a second. On Telegram the plugin's API throttler spaces messages to one private chat about a second apart, so latency there mostly reflects that pacing.

In every mode `evidence.json` records `workload` and each turn's `reply` length and SHA-256. With a provider it also records, per turn, `provider.methods` (every provider call except Telegram's `getUpdates` polls, with `:rejected` when the provider refused it), `provider.sends`, `provider.rejectedSends`, `firstOutboundMs` (the first send attempt), `lastOutboundMs` (the accepted last message) and `provider.digest` over the delivered message bodies; the run fails if any turn has a rejected send. `bus` points to `provider-api.jsonl`, Crabline's record of the requests it received; the Slack calls the front answers are not in it. `--reply-chars N` replaces the short reply with a generated technical Markdown answer of at least N characters (headings, lists, links, inline code with `<` and `&`, fenced TypeScript) and the same length on every turn. At the default limits, 10,000 goes out as four Telegram messages and 20,000 as three Slack messages.

For SQL measurement, set `OPENCLAW_CHANNEL_BENCH_NODE_OPTIONS` to the native SQL and causal tracing preloads. The Gateway receives `SQLMEASURE_OUT` pointing to the artifact directory; `phase`, `trace-map.json` and `channel-turns.json` are published atomically for observers. Preserve source maps and count all worker threads as well as Gateway MAIN. Report causal counts separately from wall-window/background counts and report latency as instrumented when preloads are active. The benchmark does not enable diagnostics or alter product sources.

This fixture covers the common channel boundary, not every transport. In every mode its open direct-message policy and asserted sender do not exercise pairing, verified user-profile identity lookup, explicit conversation bindings, attachments, group policy, or external APIs; the Telegram and Slack modes talk to local Crabline servers, and the Slack `users.info` answer is a fixed stub. Attribute those paths with separate fixtures before claiming channel-wide savings. Inbound session recording and pending-final custody use the shared session owner; an apparent channel cost is not necessarily channel-owned SQL.
