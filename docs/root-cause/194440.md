# PR 194440 root cause

Checked against GitHub Actions run [42341999366](https://github.com/openclaw/openclaw/actions/runs/42341999366), job `checks-fast-baseline-ratchets` [128311760187](https://github.com/openclaw/openclaw/actions/runs/42341999366/job/128311760187), at head `fb8c4a8088a105655ba44269689b45c23333401c`.

## What failed

The job exited 1 because `test-lines` exited 1. Its output was:

`Test lines: 6556763; ceiling: 6556684; over by: 79; net delta: +175.`

`line-cap` printed `700 -> 701 counted lines (cap 700)` and then `[ok] line-cap`. `scripts/lib/check-limits.mts` treats limit violations as advisory when `GITHUB_ACTIONS=true`, so that 701-line result did not fail the job. It does fail the same command outside GitHub Actions.

The comparison commit was `e814c50ed66c1c3849e596e32324c22100034f1c`, fetched as `origin/ci-ratchet-base`. The checkout was merge commit `b385b02d3890ba257630fb0223e0be2e771961bc`, whose parents are that base and `fb8c4a8`. The ratchet arguments were `--base refs/remotes/origin/ci-ratchet-base --no-merge-base`. Current `main` (`2e83d371655d90085fc0241baeaa332584a56dd4`) still has the same `src/infra/state-migrations.media-persistence.ts` blob as `e814c50`.

## Counted lines

The count is oxlint `eslint(max-lines)` with `{ max: 700, skipBlankLines: true, skipComments: true }` from `.oxlintrc.json` for `src/**/*.ts`. `scripts/check-line-cap-ratchet.mts` reads `File has too many lines (N).` The allowance is `max(cap, base count)`. A probe with `max: 1` forces the same counter to report files under 700. Directive tokens were neutralized the same way as the ratchet, but this file has none.

`7ad9764` did not raise the branch file to 701. It changed this file by 6 insertions and 1 deletion, and the counted total moved 680 to 685. `fb8c4a8` does not change the file. Upstream independently grew it to 696 counted lines, still under the cap, so the allowance stayed 700. The merge applied the fix's five counted lines on top of that 696 and produced 701. The warning text `700 -> 701` is the cap used as the allowance, not a measurement that the base file had 700 counted lines.

## Test lines

`scripts/check-test-lines-ratchet.mts` counts literal LF bytes in test files. From `3259404` to `fb8c4a8` the two touched test files grew by 72 and 103 LF bytes, which is the CI net delta of +175. `7ad9764` contributed 28 and 46 of those lines. `fb8c4a8` contributed 45 insertions and 1 deletion, plus 57 insertions. Upstream's ceiling had 96 lines of room (`6556684 - 6556588`). Adding 175 crossed it by 79.

## Why earlier validation missed it

Round 2 ran the test-line ratchet with `--base 7ad9764`. That tree's own baseline still had slack (`6385187` against ceiling `6398180`). The production file on that base is 685 counted lines, under 700, so the line-cap ratchet had nothing to report. Neither check built the pull-request merge against upstream `e814c50` or passed `--base <that SHA> --no-merge-base`.

## Prevention

Before pushing, merge the current upstream base in a throwaway tree and run `check:line-cap-ratchet` and `check:test-lines-ratchet` with `--base <upstream-base> --no-merge-base`. Do not use `HEAD^` or `7ad9764` as that base. A file within five counted lines of the cap on upstream cannot absorb this fix inline. The quarantine-record decision added to `migrateAgentDatabase` belongs in a sibling module, so the merge does not grow `state-migrations.media-persistence.ts`. New test lines beyond upstream slack need a justified `config/test-lines-allocations/<change>.txt` credit no larger than the added LF delta. That is the ratchet's own remedy. It is not a reason to delete tests or to change the 700-line cap.
