# openclaw-iroh-node

Node.js binding (napi-rs v3) for the part of [iroh](https://github.com/n0-computer/iroh) 1.4.1 that the
OpenClaw ID tunnel needs: bind an endpoint, dial or accept connections, open bidirectional streams, and
close with numeric codes. Stream bytes cross the boundary as `Buffer`/`Uint8Array`, never as
`Array<number>` (the cause of the ~8 MB/s cap in `@number0/iroh`).

Nothing in OpenClaw loads this package yet, and it is not published; see [PACKAGING.md](PACKAGING.md)
for the proposed distribution. Its JS API is the tailcat spike binding's, unchanged; see
`index.d.ts` (generated) for the full surface.

This crate is its own Cargo workspace. It is not a member of `crates/Cargo.toml`, so the shared Rust
workspace job does not compile iroh. `.github/workflows/iroh-node.yml` builds and tests it, only when
this directory or that workflow changes: linux x64 (gnu) runs Clippy, the tests, wire compat and the
throughput check; linux arm64, darwin arm64 and win32 x64 build and run `test/binding.test.cjs`.

## Build

Needs Rust 1.93 or newer and Node 22 or newer.

```bash
cd crates/openclaw-iroh-node
npm run build   # napi build --platform --release --strip; writes iroh-node.<platform>.node
```

`index.js` and `index.d.ts` are generated by `@napi-rs/cli` during the build. Commit them when the
Rust API changes; never edit them by hand.

## Test

```bash
npm test
```

- `test/binding.test.cjs` needs no network services: API shape, direct echo, peer identity, close
  codes and reset codes.
- `test/compat.test.cjs` starts its own dev `iroh-relay` 1.4.1 on a free loopback port and checks
  this binding against `@number0/iroh` (both directions, relay and direct paths, close codes) and
  against the tailcat spike's Rust `tunnel-testserver` (`openclaw/tunnel/0`). Each group skips when
  its dependency is missing: `IROH_RELAY_BIN` (default `~/.cargo/bin/iroh-relay`, install with
  `cargo install iroh-relay@1.4.1 --locked --features server`), `IROH_NUMBER0_DIR` (a directory
  whose `node_modules` holds `@number0/iroh@1.2.0`) and `TUNNEL_TESTSERVER_BIN`.
- `test/throughput.test.cjs` (opt-in, `IROH_NODE_BENCH=1`, release build) downloads 256 MiB on one
  stream and 8 x 64 MiB in parallel from a peer process and fails below `IROH_NODE_MIN_MBPS`
  (default 100) or when the parallel download grows RSS by more than `IROH_NODE_MAX_GROWTH_MB`
  (default 80).

## Memory

`RecvStream.read` copies the received bytes into a JS-owned `Buffer` and frees the Rust `Vec` at
once. V8 already counts external Buffers in `process.memoryUsage().external`, so
`napi_adjust_external_memory` would only double-count them. The growth came from the Rust side: each
external Buffer kept its 1 MiB read `Vec` alive until a later GC, and glibc's per-thread arenas
kept that memory after the frees. Smaller read sizes did not help (measured at 64 and 256 KiB).

`node test/support/measure.cjs --n 5 --cases down:256,streams8:512,conns8:512` prints the same
measurements (MB/s, peak RSS, RSS growth, CPU seconds per MB) without thresholds.
